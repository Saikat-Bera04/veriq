## 1. Threat Model & Security Posture

Veriq operates under a **zero-trust model regarding RPC providers and network intermediaries**:
- **Threat Actors Considered:**
  1. **Malicious or Compromised Execution RPCs:** Providers that manipulate account balances, tamper with storage slots, return forged bytecode, or return proofs from stale/reorged blocks.
  2. **Colluding RPC Providers:** Multiple providers sharing upstream infrastructure or returning matching fraudulent state.
  3. **Network Adversaries:** BGP hijackers, rogue Wi-Fi/ISP routers, or surveillance entities intercepting plaintext RPC traffic or logging IP addresses.
  4. **Contract Impersonators / Phishers:** Attackers leveraging EIP-7702 delegation to install drainer contracts on user EOAs.
- **Trusted Computing Base (TCB):**
  1. The local engine daemon (`127.0.0.1:8547`) and local client browser memory.
  2. The cryptographic strength of the Keccak-256 hash function and secp256k1 signatures.
  3. The Ethereum Beacon Chain consensus committee and weak-subjectivity beacon checkpoint.

## 2. Security Controls & Audit Findings

### 2.1 Private Key Handling & Credential Containment
- **Audit Result:** **SECURE / CONFINED**
- **Findings:**
  - The Veriq engine **never** manages, stores, asks for, or signs with Ethereum private keys. All reads are strictly read-only (`eth_getBalance`, `eth_getStorageAt`, `eth_getCode`, `eth_getTransactionCount`, `eth_getProof`).
  - Deployer keys for the demo contract (`DEPLOYER_PRIVATE_KEY`) are read strictly from ephemeral shell environments in Foundry scripts and are never committed.
  - A full repository grep confirmed zero private key occurrences or seed phrases across all tracked git commits and build bundles.

### 2.2 RPC Credentials & URL Redaction
- **Audit Result:** **SECURE / HARDENED**
- **Findings:**
  - Execution provider endpoints (`VERIQ_PROVIDERS`) typically contain sensitive API keys in their URL path (e.g. `https://eth-sepolia.g.alchemy.com/v2/<API_KEY>`).
  - In [`probe.rs`](file:///Applications/Development/veriq/backend/crates/router/src/probe.rs#L24), `ProviderCapabilities` deliberately omits the endpoint URL from `Debug` implementations.
  - In [`logging.rs`](file:///Applications/Development/veriq/backend/crates/server/src/logging.rs#L22), all emitted tracing logs pass through regex and byte-level sanitizers that scrub URLs (`[REDACTED_URL]`), private keys (`[REDACTED_PRIVATE_KEY]`), named secrets (`api_key`, `token`, `secret`), and raw IP literals.
  - Test verification: [`logs_contain_no_address_url_or_key`](file:///Applications/Development/veriq/backend/tests/integration/logs_redaction.rs) passes.

### 2.3 CORS & Localhost Isolation
- **Audit Result:** **RESTRICTED BY DEFAULT**
- **Findings:**
  - In [`http.rs`](file:///Applications/Development/veriq/backend/crates/server/src/http.rs#L26), the engine restricts cross-origin browser requests:
    ```rust
    pub const ALLOWED_ORIGIN: &str = "http://localhost:3000";
    ```
  - For production hosted environments (e.g. Render), CORS can be extended via `VERIQ_ALLOWED_ORIGINS` to allow only the Vercel dashboard origin. Arbitrary origin wildcards (`*`) are disallowed.

### 2.4 Denial-of-Service & Resource Bounds
- **Audit Result:** **HARDENED**
- **Findings:**
  - Proof parsing in [`bounds.rs`](file:///Applications/Development/veriq/backend/crates/verifier/src/bounds.rs) enforces strict limits before allocating memory:
    - Maximum proof nodes: `64`.
    - Maximum single node byte size: `1,024 bytes`.
    - Maximum HTTP response body size: `2,097,152 bytes` (2 MiB decompressed).
  - Gzip decompression bombs are prevented by streaming decompressed byte counts in `provider.rs`.
  - Tested in unit tests: `oversized_node_is_rejected_before_verification` and `gzip_bomb_is_rejected_by_decompressed_size` pass.

### 2.5 Replay Attacks & Trust Receipt Tampering
- **Audit Result:** **CRYPTOGRAPHICALLY PROTECTED**
- **Findings:**
  - Every Trust Receipt generated by [`receipt.rs`](file:///Applications/Development/veriq/backend/crates/core/src/receipt.rs#L12) contains:
    - `requestBinding = keccak256(method + canonical_params)`
    - `resultBinding = keccak256(canonical_value)`
    - `block = { number, hash, stateRoot, finalized }`
  - A recipient or auditor can independently recompute the bindings to confirm that the receipt was not attached to a different request or manipulated after the fact.
  - Receipts stored in PostgreSQL are indexed with a transaction-scoped retention lock (`RETENTION_LOCK_ID`) preventing concurrency race conditions.

### 2.6 Privacy Downgrade Invariant
- **Audit Result:** **FAIL-CLOSED**
- **Findings:**
  - When a client sets `privacy: "required"`, the engine strictly forbids direct connections to providers.
  - If private transport (Nox/Nym/Tor) is unavailable or fails, Veriq immediately terminates the read with `PRIVACY_UNAVAILABLE (-32013)`.
  - Tested in `tests/integration/privacy_required.rs`: `privacy_required_sends_nothing` asserts that zero HTTP requests are transmitted to execution providers when privacy is required and unavailable.

### 2.7 Production Debug Endpoints
- **Audit Result:** **ISOLATED UNDER FEATURE FLAGS**
- **Findings:**
  - Administrative breaker reset endpoints (`POST /admin/reset-breakers`) are compiled strictly under the `--features demo` cargo flag.
  - Production engine builds omit this flag, ensuring that external entities cannot reset breaker states or trigger attack simulations.
  - The malicious RPC proxy (`veriq-malicious-rpc`) is a separate binary that is never bundled with production engine releases.

## 3. Vulnerability Matrix & Recommended Hardening

| Issue | Severity | Status | Mitigation in Place | Recommended Future Action |
|---|---|---|---|---|
| Weak-Subjectivity Checkpoint Aging | **MEDIUM** | Mitigated | Engine refuses to start if checkpoint is older than weak-subjectivity period (~2 weeks). | Implement automated periodic checkpoint sync daemon for long-running deployments. |
| In-Memory Cache Snooping | **LOW** | Mitigated | Engine runs on loopback `127.0.0.1:8547` with restricted CORS. | For shared multi-user servers, require Unix domain socket authentication. |
| Hosted Engine Relay Trust | **LOW** | Resolved in S5 | When using a hosted engine, client relies on engine for receipt generation. | S5 in-browser WASM verifier checks proofs client-side, allowing offline and untrusted hosted operation. |
